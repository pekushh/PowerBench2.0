# PowerBench

**Бенчмарк схем управления электропитанием Windows для игровых рабочих нагрузок.**

PowerBench измеряет, насколько каждая схема питания реально влияет на
производительность CPU-bound игры, и говорит, какую схему стоит включить.
В отличие от обычных «переключил и на глаз» сравнений, он не даёт одну цифру,
а показывает **разницу с доказательностью**: «эта схема лучше той на 2,3 % с
95 %-й уверенностью» или «разницы нет, выбирайте по вкусу».

Работает только на Windows 10/11 x64.

## Что это и зачем

Схемы питания в Windows (`Сбалансированная`, `Высокая производительность`,
`Максимальная производительность`, ваши собственные) меняют десятки параметров
управления процессором: агрессивность разгона, пороги переключения P-состояний,
политику охлаждения, отключение таймеров. На глаз разницу не видно — она
измеряется процентами.

PowerBench воспроизводит нагрузку, близкую к игре (постоянная нагрузка на ядра, а
не «открыть архив и ждать») и измеряет её честно:

- **детерминированно** — фиксированный seed, фиксированный порядок задач,
  контрольные суммы каждого тика. Два запуска дают побайтово одну картину,
  поэтому разницу между схемами видно, а разницу между запусками — нет;
- **по фазам** — лёгкая, частичная, тяжёлая, отклик: видно не только «среднее»,
  но и как схема ведёт себя в конкретных режимах;
- **с проверкой среды** — замер не начнётся на батарее, с чужой фоновой
  нагрузкой выше порога или без прав администратора;
- **с восстановлением** — исходная схема питания возвращается автоматически,
  даже если программу закрыли посреди сессии.

## Быстрый старт

### Нужно

| Требование | Почему |
|---|---|
| Windows 10 или 11, x64 | используются `powercfg` и Windows API для управления питанием |
| Права администратора | переключение схем питания и чтение состояния процессора |
| Питание от сети (AC) | на батарее замер не запускается — результат был бы бессмысленным |
| Минимум 2 схемы питания | сравнивать нечего |
| 250 МБ свободного места | проверка готовности не запустит замер при меньшем свободном месте |

Приложение само проверяет эти условия перед стартом и объясняет, что именно
не так, — отдельно ничего проверять не нужно.

> Сборка проекта возможна на любой ОС (тесты CI идут и на Linux), но
> **работоспособен** PowerBench только под Windows: вне её нет `powercfg` и
> Windows API. Поддерживается и тестируется Windows x64.

### Графический интерфейс

1. Запустите `powerbench-app.exe` **от имени администратора**.
2. Пройдите проверку готовности — приложение само проверит права, питание,
   наличие схем и свободное место.
3. Выберите режим: **Быстро** (скрининг) или **Детально** (сравнение).
4. Отметьте схемы питания для сравнения.
5. Запустите замер. Схемы переключатся сами; после каждого прогона есть пауза
   на охлаждение.
6. На финише — рекомендация с уровнем доказательности и кнопка
   **«Применить лучшую схему»**, которая включает победителя в Windows.

Замер можно прервать и продолжить позже: прогрены сохраняются в контрольную
точку, а `resume` продолжает с того же места.

### Консольный интерфейс

```powershell
powerbench-cli list                                  # какие схемы есть
powerbench-cli bench --preset quick --schemes "<guid1>,<guid2>"
powerbench-cli history list                           # что сохранилось
powerbench-cli history export all --format csv --out .\exports
powerbench-cli --help                                # все подкоманды и флаги
```

`powerbench-cli` без подкоманды запускает самопроверку ядра — она печатает в
консоль, проходит или нет, и годится для проверки сборки на чужой машине.

Полный список параметров — в [`bench.example.toml`](bench.example.toml).

## Как читать результат

Главное в отчёте — не «средняя скорость», а **рекомендация с уровнем
доказательности**. Уровень отвечает на вопрос «насколько можно доверять
выводу», а не «насколько велика разница».

| Уровень | Что значит | Когда выдаётся |
|---|---|---|
| `Подтверждено` | Разница доказана | ≥3 прогона, разброс ≤2 %, перевес ≥1 %, P(перевес>1 %) ≥95 %, P(лучший) ≥90 % |
| `Вероятно` | Разница вероятна | ≥3 прогона, перевес >0, P(перевес>0) ≥80 %, P(лучший) ≥60 % |
| `Практическая ничья` | Схемы неразличимы, выбрана лучшая по качеству хвоста | перевес в пределах 1 %; сравниваются по очереди P1 → стабильность → разброс → P0,1, и берётся **первый** применимый критерий |
| `Предварительно` | Пока рано судить | данных мало или высокая неопределённость |
| `Скрининг` | Замер только отсеивает | если хотя бы одна схема отмерена один раз (то есть любой замер в режиме «Быстро») |
| `Оставлена текущая` | Ничья, и переключать нечего | разницы нет, а менять схему не хочется |
| `Эквивалентны` | Разницы нет вовсе | схемы статистически неразличимы |
| `Нет данных` | Сравнивать нечего | нечего сравнивать |

Как это читать на практике:

- **`Подтверждено`** — можно включать смело.
- **`Вероятно`** — скорее всего лучше, но стоит перепроверить на своей
  рабочей нагрузке.
- **`Скрининг`** — вы запустили «Быстро». Это не «слабый результат», а честное
  «данных для вывода ещё нет»: повторите в режиме «Детально».
- **`Предварительно`** — данных мало (например, прервали сессию). Повторите
  замер в режиме «Детально».
- **`Практическая ничья` / `Оставлена текущая` / `Эквивалентны`** — разницы нет.
  Переключать схему ради переключения не нужно.

### Как читать числа

В отчёте и в приложении это называется так:

- **Медиана, тик/с** — основная величина. Считается по **медиане** прогонов:
  медиана нечувствительна к одному выбросу, среднее — нет. Выше — лучше.
- **P1 (мин. 1 %)** — «худшая секунда»: установившийся темп, при котором
  система ещё держит скорость. Это **пессимистичный хвост**, поэтому
  *ниже* — хуже. Именно поэтому при ничьей решает он, а не медиана.
- **Разброс (CV)** — насколько стабильны повторы между собой. Большой разброс
  означает, что машина «гуляла», и результату нельзя доверять.
- **Стабильность** — не разошлись ли результаты разных фаз в разные стороны.
  Схема может быть быстрой в лёгкой фазе и проваливаться в тяжёлой — это
  видно здесь.
- **Перевес против эталона** — насколько схема обгоняет схему, взятую за
  опорную. Эталон выбирается автоматически (обычно это текущая активная схема),
  и именно против него считается «перевес» в рекомендации.

P0,1 (ловушка кратковременных остановок) и «худшая секунда» в смысле минимума
по секундным окнам считаются во внутренней статистике и в паричьях, но в
таблицу отчёта не выводятся — в отчёте «худшая секунда» это как раз P1.
Путать эти две вещи не стоит: P0,1 ловит микрофриз, P1 — устойчивое падение.

Важное ограничение: сравнивать можно только результаты **одной и той же
конфигурации**. Для этого у каждого замера есть «хэш конфигурации» — если у
двух записей он разный, цифры сопоставимы лишь приблизительно.

## Из чего состоит замер

Один прогон — это четыре фазы, и в каждой своё поведение схемы. Длительность
делится по правилу: **база 4 с на казу** (минимум замера 16 с), а остаток
свыше этих 16 с делится так: **30 % лёгкой, 20 % частичной, 35 % тяжёлой**, и
всё, что осталось, достаётся «Отклику».

| Фаза | Что проверяет |
|---|---|
| **Лёгкая** | Ровная умеренная нагрузка: базовая эффективность |
| **Частичная** | Занята половина ядер. Различие схем тут максимально |
| **Тяжёлая** | Все ядра под нагрузкой: установившаяся производительность и троттлинг |
| **Отклик** | Кратковременные пики: как схема возвращается в строй |

Из этого следует, что доли фаз **не равны** их процентам: проценты применяются
к остатку свыше 16 с, поэтому на коротком замере они сближаются (на 30 с
получается 8 / 6 / 8 / 8 с), а на длинном «Отклик» получает заметно больше
15 %.

Плюс разогрев (профиль «Отклик») и пауза охлаждения между прогонами — чтобы
схема успевала вернуться в исходное состояние и «отдыхнуть».

## Режимы и параметры

| Пресет | Длительность | Разогрев | Охлаждение | Раундов | Фазы этой длительности | Для чего |
|--------|-------------|----------|------------|---------|-----------------------|----------|
| `quick` | 30 с | 3 с | 3 с | 1 | 8 / 6 / 8 / 8 | Скрининг: отсеять явно слабые схемы |
| `detailed` | 60 с | 8 с | 5 с | 5 | 17 / 12 / 19 / 12 | Сравнение (по умолчанию) |

- **`quick`** — один раунд, доверительный интервал не строится, и уровень
  доказательности будет `Скрининг`. Он честно называется скринингом: годен,
  чтобы убрать очевидно плохие схемы, но не для выбора победителя.
- **`detailed`** — минимальный пресет, на котором адаптивная остановка вообще
  срабатывает: если перевес уже доказан, остальные прогоны не нужны и сессия
  заканчивается раньше.

Параметры переопределяются флагами: `--duration`, `--warmup`, `--cooling`,
`--reps`, а также `--workers`, `--threshold`, `--plan`, `--out`,
`--allow-dirty-background`. Полный список и границы — в
[`bench.example.toml`](bench.example.toml) и в `powerbench-cli --help`.

Границы: длительность 16…3600 с, разогрев от 2 с, охлаждение 0…60 с,
повторов 1…9.

## Если замер не запускается

| Симптом | Причина | Что делать |
|---|---|---|
| «Окружение не готово» | нет прав администратора | запустите от имени администратора |
| Не запускается на батарее | питание не от сети | подключите зарядное устройство |
| «Фон выше порога» | другая программа нагружает CPU | закройте тяжёлое или продолжите с риском осознанно |
| Схема не переключается | политика группы / сторонний OEM-агент | проверьте, что план применён, иначе верните схему вручную |
| «Питание пропало посреди сессии» | кабель или отключение от сети | сессия остановлена целиком, чтобы результаты не смешались |
| После прерывания спрашивает про восстановление | осталась контрольная точка | продолжите замер или откажитесь — исходная схема будет возвращена |

Исходная схема питания восстанавливается автоматически при завершении, при
ошибке и при прерывании процесса. Если программу убили жёстко, при следующем
запуске приложение предложит вернуть схему — консольная команда
`powerbench-cli status` покажет состояние контрольной точки.

## Где лежат данные

Всё лежит в `%LOCALAPPDATA%\PowerBench\`:

| Что | Зачем |
|---|---|
| история сессий (JSON) | результаты прошлых замеров, экспорт в CSV/JSON |
| HTML-отчёты | готовый отчёт для отправки или архива |
| `benchmark-checkpoint.json` | незавершённая сессия для `resume` |
| логи | журнал сессии для разбора проблем |

Из приложения: **Результаты → Папка** открывает этот каталог.

```powershell
cd app
```

контракт окна, плотность и масштаб текста.

### Структура

```
core/         ядро нагрузки GamingCpuV1: движок, пул воркеров, контрольные суммы
metrics/      статистика: перцентили, окна, стабильность, агрегация
recommend/    рекомендации: bootstrap, доверительные интервалы, уровни доказательности
windows/      Windows API: powercfg, приоритет, сон, питание, мониторинг процессов

cli/          консольный интерфейс и самопроверка ядра
app/          Tauri-приложение (React + TypeScript)
```

### Детерминизм

- **Seed** `0xC52A202600000001`, зафиксирован в спецификации.
- **Хэш конфигурации** — SHA-256 от параметров профилей нагрузки. Заморожен
  строкой в коде и проверяется самопроверкой: изменилась хоть одна константа
  объёма работы — прогоны разных сборок больше нельзя сравнивать, и валидатор
  об этом скажет.
- **Порядок схем в раунде** — детерминированная ротация против «кто первый»
  (`cycle = round / n`; чётный цикл — прямой порядок, нечётный — реверс, сдвиг
  `round mod n`). Иначе одна и та же схема систематически мерялась бы в
  невыгодное время и результат зависел бы от порядка в списке.
- **Контрольные суммы** — цепочка миксов, проверяется при каждом сбросе.
